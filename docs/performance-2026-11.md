# 效能優化紀錄（2026-11）

原則：不改功能、資料結構、操作流程與畫面。資料庫變更需確認後才執行。

## 一、檢測方式

- 前端：正式版（Supabase）與預覽版（mock）各自建置，以 gzip 靜態伺服器模擬 GitHub Pages。
  Chromium 模擬慢速網路（1.6 Mbps、150 ms 延遲）與 CPU 降速 4 倍，各情境取中位數。
- 資料庫：在正式資料庫以「交易內建立測試資料、最後全部還原」的方式，模擬 2,000 筆會議量測查詢時間，不留下任何資料。

## 二、發現的問題

| # | 優先 | 問題 | 原因 | 處理 |
|---|---|---|---|---|
| 1 | 高 | 正式版每次開啟都執行「預覽用模擬後端」 | `services/api.js` 同時 import 兩種後端；模擬後端載入時會建立示範資料、寫入 localStorage、執行 4 次 PBKDF2 雜湊 | ✅ 建置時只打包實際使用的後端 |
| 2 | 高 | 登入頁就下載全部程式（編輯器、後台、日期選擇器） | 沒有依頁面分割程式碼，所有頁面都在主程式內 | ✅ 依頁面延後載入，登入後背景預載常用頁面 |
| 3 | 高 | 會議列表查詢隨會議數量急遽變慢（2,000 筆約 3.7–6 秒） | `list_meetings()` 對每一筆會議各呼叫 5 個權限函式（逐列子查詢） | ✅ 改為整批計算（實測 6,075 ms → 194 ms，結果完全相同）`20261128120000_perf_list_meetings_rls.sql` |
| 4 | 中 | 登入後資料請求串行等待 | `me()` 依序查個人資料→角色；使用者名單→會議列表依序執行；進入列表又重抓一次使用者名單 | ✅ 改為同時查詢，30 秒內不重抓 |
| 5 | 中 | 回到會議列表整頁顯示載入中並重抓 | 每次切換都非背景重抓 | ✅ 先顯示既有資料，背景更新 |
| 6 | 中 | 多人編輯時每台電腦不斷重抓會議列表 | 任何人修改會議資料都觸發所有人重抓，即使不在列表頁 | ✅ 只有在列表頁才立即重抓，其他頁面回來時再更新 |
| 7 | 中 | 通知每分鐘輪詢，分頁在背景也照常 | 已有即時推播，輪詢只是備援 | ✅ 改為 5 分鐘、背景暫停、切回分頁時立即更新 |
| 8 | 中 | 部分資料表的權限規則逐列重算 | `profiles`、`audit_logs` 的 RLS 未以 `(select …)` 包住函式 | ✅ 同上 migration |
| 9 | 低 | Google 字型樣式表阻擋首次繪製 | 同步載入的 stylesheet | ✅ 改為非阻擋載入（字型仍使用 display=swap） |
| 10 | 低 | 標誌圖檔偏大 | PNG | ✅ 改為無損 WebP（像素完全相同），48.8 KB → 36.6 KB |
| 11 | 低 | 3 個外鍵沒有索引 | `app_settings`、`external_members`、`role_permissions` | 不處理：資料量極小，加索引沒有效益 |

已確認不是瓶頸、不需處理：會議／帳號列表已分頁（2,000 筆時 DOM 約 450 個節點，不需虛擬捲動）；搜尋、篩選、排序在前端以 `useMemo` 計算；通知、修改紀錄、異動紀錄已有筆數上限。

## 四、修改的檔案

- `vite.config.js`：`@backend` 別名依環境選擇後端；日期選擇器、語音辨識、向量化套件不放進每頁載入的 vendor；單檔預覽清除預載佔位符
- `src/services/api.js`、`backend.supabase.js`、`backend.mock.js`（新增）、`devFlags.js`（新增）、`mockServer.js`、`features/speech/useSpeechToText.js`：後端拆分
- `src/App.jsx`：頁面延後載入與預載、請求並行、使用者名單快取、列表背景更新、即時更新只在列表頁重抓
- `src/main.jsx`、`components/common/pickers.jsx`：日期選擇器的 LocalizationProvider 移到選擇器內
- `src/services/supabaseApi.js`：`me()` 平行查詢；修改紀錄、異動紀錄只取需要的欄位
- `src/components/layout/NotificationBell.jsx`：輪詢策略
- `src/components/auth/AuthForm.jsx`、`src/assets/auth/*.webp`：圖檔格式
- `index.html`：字型非阻擋載入
